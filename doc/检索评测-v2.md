# 检索评测 v2：接入 Zotero 识别服务

> 日期：2026-10-11　分支：`feat/zotero-recognizer`　环境：macOS 27 / Swift 6.4　对应需求：META-02 第 0 条、META-06

## 1. 结论

- 新引擎（接入 Zotero 识别服务）在正常网络下与旧引擎准确率持平：两者都是 **0 错误匹配**，命中率都在 99%–100%。差的那 1 篇是偶发网络超时，单独重跑时命中。
- 识别服务的价值在开放数据源不可用的时候。模拟"标题检索全部不可用"（Crossref 宕机、OpenAlex 额度用完、DBLP 反爬虫）时，命中率从 **92.4% 提高到 97.5%**，P90 从 5.01 s 降到 4.17 s。
- 新引擎会选正式发表的版本：有 3 篇论文，旧引擎给出 arXiv 预印本，新引擎给出 CVPR / ICCVW / WACV 的正式 DOI。按评测规则两者都算正确。
- 耗时：中位数基本不变（1.90 s → 1.99 s）；P90 从 4.06 s 升到 4.86 s，仍在需求的 5 s 以内（原因见第 5 节）。
- 评测中发现并修复了 2 个问题（第 4 节），其中一个会造成错误匹配。修复后重跑，4 种配置都没有错误匹配。

## 2. 样本与方法

**样本**：你的 Zotero 库中所有"有父条目的 PDF 附件"，共 119 篇。

- 取样方法：先把 `~/Zotero/zotero.sqlite`（连同 `-wal`）复制到临时目录，再只读这份副本；PDF 在原位置只读打开。`~/Zotero` 下没有写入任何文件。
- 按版本分：67 篇原版 PDF，52 篇翻译插件生成的中英对照版（`*.compare.pdf`）。
- 按父条目类型分：期刊文章 53、预印本 33、会议论文 19、网页 13、图书章节 1。
- 另有 22 个没有父条目的独立 PDF，因为没有真值，不计入样本。

**真值**：父条目的标题、DOI、年份。只要满足下面任一条，就判为正确：

- 返回结果的标题与真值标题的标准化相似度 ≥ 0.9（`TitleNormalizer`）；
- DOI 与真值相同。

找到了结果但不正确，记为"错误匹配"。

**对比方式**：

- 旧引擎 = `useZoteroRecognizer = false`，新引擎 = 默认配置。
- 和 App 一样每批 4 个文件并发。每批中两个引擎都跑一遍，先后顺序逐批交替，让两者遇到相同的网络状况和服务端缓存。
- 断网模拟：所有标题检索请求（Crossref 检索、OpenAlex、DBLP、arXiv 检索）直接返回 503；标识符查询和识别服务照常可用。
- 识别服务单独探测：对每个文件单独调用一次识别服务，记录它返回了什么、耗时多少。

**复现命令**：
```
cd Packages/FolioCore
FOLIO_LIVE=1 FOLIO_EVAL_OUTAGE=1 FOLIO_EVAL_REPORT=/tmp/eval.tsv swift test --filter ZoteroCorpusEvaluation
```
可选环境变量：`FOLIO_EVAL_ONLY=<附件 itemID,…>` 只跑指定文件；`FOLIO_EVAL_LIMIT=<n>` 只跑前 n 个；`FOLIO_EVAL_PROBE=0` 跳过识别服务单独探测；`FOLIO_ZOTERO_DIR` 指定 Zotero 目录。

## 5. 评测中发现并修复的问题

| # | 现象 | 原因 | 修复 |
| --- | --- | --- | --- |
| 1 | 2/119 篇（TopoTTA 原版和对照版）的识别请求在本地就失败了，没有发出 | PDFKit 把部分字形报告成孤立的 UTF-16 代理项，`JSONSerialization` 无法编码，导致整个请求体被丢弃 | 读字符时先修复编码，没有文字映射的字形直接跳过（`RecognizerPayload.character(in:range:)`），并补了单元测试 |
| 2 | 模拟检索不可用时出现 1 篇**错误匹配**（第 57 号）：标题被识别成作者行 | 识别服务把作者行当作标题返回。这段文字本来就在首页上，又有 6 个以上的词，所以"标题出现在首页"的核对照样通过。可见对识别服务从页面上读出来的字段，首页核对本身没有意义 | 识别服务只给字段时，标题还必须与引擎自己排第一的标题猜测相似度 ≥ 0.9（`CandidateScorer.acceptsRecognizedFields`）。不能用"任一猜测"，因为排名靠后的猜测本身就可能是作者行。修复后重跑，4 种配置都是 0 错误匹配 |
| 3 | 单元测试发现：带"Abstract"标题的摘要，末尾句号被去掉了 | `FieldNormalizer.cleanAbstract` 去掉标题后，对字符串两端都做了裁剪 | 只裁剪开头 |

## 6. 耗时分析

- **中位数**：基本不变。原因是识别服务和现有查询同时启动：PDF 自身标识符核对通过时，照旧立即返回，不等识别服务。
- **P90 上升（4.06 s → 4.86 s，均值 2.36 s → 2.67 s）**：
  - 把最慢的几篇单独重跑（第 449、450、453、52 号），新旧引擎耗时相同：中位数 2.37 s 对 2.69 s，P90 3.75 s 对 3.66 s。所以差距不是固定的等待逻辑造成的，而是批量运行时的网络竞争。
  - 新引擎每篇多上传约 0.5 MB，经过代理时会和同批的其他请求争带宽。
  - 识别服务给出的 arXiv ID 要查 arXiv，会多占 arXiv 每秒 1 次的限流配额，让同批其他文件排队更久。
  - 评测期间 Crossref、OpenAlex、DBLP 多次返回 429，也放大了波动。
  - 目前没有找到既便宜又安全的改法，所以没有改动等待逻辑；P90 仍满足 META-06 的 5 s 要求。
- **为什么不压缩请求体**：实测服务端能接受 `Content-Encoding: gzip`，请求体可以压到原来的 1/5，但只快了约 0.2 s；而且这不是 Zotero 客户端使用的协议，以后可能失效，所以没有采用。

## 7. 引擎行为摘要（供集成参考）

- 识别服务与标识符查询、标题检索同时启动；构建请求体加上等待回答，总预算 4 s。识别服务给出的每个标识符，查询预算为 5 s。
- 优先级：PDF 自身标识符 > 识别服务给出的标识符 > 识别服务字段 > 标题检索结果。
  - PDF 自身标识符的查询还没结束时，已经核对通过的识别服务标识符结果会先放着，等前者结束再决定用哪个。
  - 识别服务慢的时候不会拖住已经拿到的检索结果：照常沿用原有的 0.8 s 宽限期。
- 识别服务给出的标识符查到记录后，按"标题出现在首页"核对，和 PDF 文本中找到的 DOI 用同一条规则。
- 识别服务只给字段时，必须同时满足两条才采用：
  1. 标题与引擎排第一的标题猜测一致；
  2. 通过 `CandidateScorer` 的检索候选阈值。

  如果标题检索找到的是同一篇的记录（标题相似度 ≥ 0.95、年份相差不超过 1 年、DOI 不冲突），改用检索记录，因为它带 DOI 和期刊等信息。
- 识别服务返回的摘要，会补到缺少摘要的结果里（要求标题相似度 ≥ 0.9）。
- 识别服务的任何失败（断网、4xx/5xx、超时、返回内容无法解析、空结果）都不计入"未找到 / 网络错误"的判断，原有结果不受影响。单元测试逐一覆盖了这 5 种失败情况。
- 首页靠 OCR 识别的扫描版 PDF 没有文字层，不发送识别请求。

## 8. 风险

1. **服务没有公开文档**：`services.zotero.org/recognizer/recognize` 不需要密钥，但也没有公开的接口约定，随时可能改格式、限流或下线。引擎把它当作可选数据源，所有失败都会静默退回原流程；解析时所有字段都按宽松规则读取。
2. **隐私**：开启后，每个 PDF 的前 5 页文字及其位置、字体，以及文件名和 PDF 文档信息（Title、Author、Creator 等）都会发给 Zotero。这和 Zotero 自己的"获取 PDF 元数据"功能一样。请求头只带 `Folio/1.0`，不附带设置里的联系邮箱。应在设置中说明，并提供开关。
3. **流量**：每个 PDF 上传约 0.5 MB。批量导入 100 篇大约 50 MB。
4. **中英对照版效果差**：对照版有 3–5 篇识别失败，其中 2 篇把作者行当成了标题。错误结果现在会被拒绝，但这类 PDF 主要还得靠开放数据源。
5. **arXiv 限流**：识别服务给出 arXiv ID 时，会多发一次 arXiv 查询；如果 PDF 本身已有这个 ID，会去重，不重复查询。批量导入时可能让 arXiv 队列稍长。

## 9. App 集成要点

- 开关：`MetadataEngineConfiguration.useZoteroRecognizer: Bool`，默认 `true`。设为 `false` 时不发送任何数据，`resolve(pdfAt:)` 的行为与 v1 完全相同。建议在设置的"检索"页加上"使用 Zotero 识别服务"开关和隐私说明，构造 `MetadataEngine` 时传入。
- `HTTPClient` 协议新增 `post(_:body:headers:)`，带默认实现（直接抛出 `URLError(.unsupportedURL)`），已有的实现类型不需要修改；`URLSessionHTTPClient` 已经实现了这个方法。
- 其余公开 API 没有变化。按开发计划，`engineRevision` 升级（让此前失败的 PDF 自动重试一次）由主 agent 在集成时处理。
