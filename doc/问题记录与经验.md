# 问题记录与经验总结

记录开发中遇到的问题、根因、解决办法；反复出现的问题会总结成经验放在文末。

## 经验总结

- **先验证外部数据源的真实行为**：Zotero 的 linkMode、OpenAlex 的额度政策都和记忆中的不同。凡是依赖外部系统的规则，写进计划之前先用真实数据核对一遍。
- **用真实数据评测检索引擎**：用用户自己的 49 篇 PDF 做在线评测，暴露出了 arXiv 限流排队和"网络错误误判为未找到"两个问题，这些靠 mock 测试发现不了。
- **NSOutlineView 有自己的缓存语义**：未加载的子项、可展开状态、正在编辑的单元格，都不会因为 `reloadData(forRowIndexes:)` 而更新。结构有变化时要整表重载，编辑期间不要刷新。
- **App target 使用默认 MainActor 隔离时**：AppKit 的重写点要标 `nonisolated`；传给 `Task.detached` 的闭包只捕获 `let` 和 Sendable 值，内层回调显式标 `@Sendable`。
- **测试不能影响用户的真实环境**：测试用临时文献库；UI 测试模式下不写入偏好设置；不运行会控制鼠标键盘的自动化（XCUITest、CGEvent、Finder 脚本），这类测试交给用户手动跑。检查界面用"启动参数进入状态 + 后台启动截图"的方式。
- **每个功能都要验证它真正的入口**：外观截图和另一条入口（`open -a`）通过，不代表拖放本身能用。无法做真实交互时，要用模拟对象调用真实的处理方法，覆盖到同一段代码。
- **重写 AppKit 方法时，不能想当然地调用 super**：协议里有声明，不代表父类有实现。拖放这类由系统回调驱动的方法，异常会被系统吞掉，只留下坏掉的状态。可以先用 `instancesRespond(to:)` 确认父类是否实现。
- **排查问题时先看运行中的证据**：`sample` 调用栈、`/usr/bin/log show` 系统日志、只读查询用户的数据库，这些都不需要操作桌面，就能直接定位到问题所在的那一行代码。
- **外部数据源会变**：DBLP、OpenAlex 都在这两天改了访问政策。检索引擎要能容忍单个来源失效，并且针对重要领域（CVF 会议）有直接的一手来源。
- **不要对可能返回 nil 的 UTType 用 `?? .data` 兜底**：这会让判断条件对所有文件都成立。自定义类型要在 Info.plist 里声明。
- **PDFKit 批处理必须包 autoreleasepool**，数据库写入要合并成事务，否则内存和界面刷新都会随文件数线性增长。
- **原生感来自"让系统画"**（v2.0 重构）：侧栏、检查器、工具栏、搜索框、标签页全部换成系统组件后，Liquid Glass、深浅色、全屏、自定义工具栏都自动生效，代码反而更少。
- **菜单快捷键优先于按键事件**：任何和文本编辑键重名的快捷键（⌘⌫、⌘↓、Home、End），都要在文本有焦点时让验证返回 false。
- **NSSplitViewController 在首次布局前会忽略折叠状态**，初始折叠要放到视图出现之后；后加入 NSSplitView 的子视图宽度为 0，需要显式设置分隔条位置。
- **PDFKit 文档用内存映射读取，再原子替换文件保存**：写回时不会和正在读取的文件冲突，外部 App 也能看到完整文件。
- **外部数据源要实测评估**：用用户自己的 119 篇 PDF 评测发现，旧引擎在网络正常时已经 100% 命中；Zotero 识别服务的价值在于开放数据源受限时的兜底（92.4% → 97.5%），这个结论只能靠真实评测得到。
- **测试和截图运行不能写用户的偏好设置**：UI 测试模式下 AppSettings 只在内存中修改。
- **第三方 Python 工具要锁定版本**：pdf2zh_next 的依赖没有锁上限，新版 bitstring 直接导致无法运行；安装命令固定版本并附加约束。
- **侧栏要用系统源列表的全部语义**：分区用 group row、层级用系统展开箭头、尺寸用 `rowSizeStyle`、焦点学 Finder 不抢；任何自绘（箭头、行高、字号）都会在系统更新或用户改了"边栏图标大小"后显得不协调。
- **菜单里的图标都是模板图**：需要在菜单中显示颜色时，画一张 `isTemplate = false` 的位图，不要依赖 SF Symbol 的调色板配置。
- **偶发的测试失败要追到底**：一次 signal 6 背后是 PDFKit 的线程安全问题，在 App 的批量导入中同样会发生。并行测试恰好是发现这类问题的压力测试。
- **改写别人的配置文件要格外保守**：优先调用对方自己的命令行（`claude mcp add`、`codex mcp add`），否则先备份、无法解析就拒绝写入，并且只删除自己写入的内容；开关状态以对方配置文件为准，而不是 Folio 自己的记录。
- **SDK 的并发标注也可能是错的**：回调被标成 `@MainActor` 却在后台队列调用时，崩溃发生在系统生成的检查里，自己的代码怎么标都没用。看到 `swift_task_checkIsolated` 的崩溃，先去 SDK 头文件里查 `NS_SWIFT_UI_ACTOR`。
- **本地服务的安全边界要两层**：只监听 127.0.0.1 挡住其他机器，检查 Origin 和自定义请求头挡住本机网页（网页表单无法设置自定义请求头，跨域的预检也会被拒绝）。
- **协议实现要读行规范，而不是用"按行读取"的便捷 API**：stdio 的 MCP 只以 LF 分隔消息，而 Foundation 的 `lines` 会在多种 Unicode 换行符处断开。用真实的客户端行为（Node 不转义 U+2028）去测，才能发现这种只在特定文字中出现的卡死。
- **对接别人的产品时，以对方当下的官方文档为准，并定期复核**：Codex、Antigravity、Windsurf 的配置或技能目录在几个月内都变过；开放技能标准的 `~/.agents/skills` 让一份文件服务多个智能体。目录信息集中在一张表里（开发计划 v2.6 §2），改动时同步测试。
- **验证集成要用对方自己的工具**：`claude mcp list`、`gemini mcp list` 会真的启动服务器并握手，比检查配置文件可靠得多；临时 HOME 能在不碰用户配置的前提下做真实验证。
- **浏览器扩展也能做真实的端到端测试**：品牌版 Chrome 不再支持 `--load-extension`，但临时配置文件 + 开发者协议 `Extensions.loadUnpacked` 可以载入扩展并在后台脚本中执行真实的识别、保存和 PDF 下载。页面识别另有固定样例页的回归测试，并用旧版代码跑一遍确认测试能发现问题。
- **"安装简单"要按用户真实看到的界面写步骤**：隐藏的 `~/Library`、Safari 的"允许未签名的扩展"这类卡点，只有沿着真实流程走一遍才会发现；安装引导应自己检测完成状态，而不是让用户判断。
- **扩展脚本保持 ASCII**：浏览器为扩展生成的页面不一定声明字符集，Safari 会按系统语言选编码。界面文字放在声明了 UTF-8 的页面里，后台和注入脚本中的非 ASCII 字符一律写成 `\u` 转义，并用测试守住。
- **"装过"不等于"能用"**：判断外部工具是否存在，要像用户那样运行它（同样的 PATH、能报告版本），而不是看它留下的文件夹。
- **文字居中要按字形，不按行高**：混排中英文时，回退字体会改变行高；在自己的胶囊、徽标里用 Core Text 指定基线，按墨迹光学居中。
